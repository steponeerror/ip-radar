# Research: Human-in-the-loop agent UX best practices (2025–2026) — autonomous ops/watchdog agent proposing actions for human approval

Date: 2026-10-23 · Scope: vendor guidance, mainstream agent-product review surfaces, ops/alerting UX, AIOps propose-then-approve patterns, blob-report vs structured-item critique. Grounding for IP Radar ops-module interaction redesign.

## Summary

The 2025–2026 mainstream consensus treats HITL as a **structured pause/resume on discrete, machine-readable action items** — never a free-text report to react to. Every major reference implementation (LangGraph Agent Inbox, OpenAI Agents SDK approvals, Claude Code plan/permission modes, GitHub Copilot PR flow, Cursor cloud agents) converges on the same affordance set — **approve / edit / respond / ignore, with tiered autonomy, consequence-labeled buttons, and audit-trail + undo** — while ops tooling (PagerDuty/Datadog) supplies the noise ladder (dedup → group → suppress → digest) that directly answers the "18 findings, 16 noise" problem. For a propose-then-approve ops agent, the actionable core is: findings become structured items with evidence/blast-radius/rollback; rulings become per-item decisions with reason capture; precedents become the same mechanism as Claude Code "allow rules" and PagerDuty grouping feedback; and the markdown report demotes to a rendering of the item set, not the review surface.

## Findings

### A. Vendor guidance (frameworks/SDKs)

1. **HITL = durable interrupt + resumable state, not a conversation detour.** LangGraph `interrupt()` persists graph state via a checkpointer and waits indefinitely; the interrupt payload (any JSON) is surfaced to the caller, and execution resumes with `Command(resume=...)` carrying the human's decision. Static breakpoints vs dynamic interrupts are both supported; interrupts can be conditional on app logic. This is the canonical "agent pauses at a decision point, human answers, agent continues" primitive. [LangChain docs — Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

2. **OpenAI's approval lifecycle is identical in shape: record interruption → pause → per-item approve/reject → resume same run.** Guardrails validate automatically (input/output/tool); *human review pauses the run so a person or policy can approve/reject sensitive actions*. Pending approvals return in an `interruptions` array; each is resolved with `state.approve()` / `state.reject()` — reject can carry a `message` that goes back to the model — and `{alwaysApprove: true}` pre-approves the same tool for the rest of the run (batching/trust-accumulation affordance). Resume continues from the interrupted point, including nested agent-tool runs. [OpenAI — Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals) · [OpenAI Agents SDK — Human-in-the-loop](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)

3. **The canonical four affordances for a "ruling face": accept / edit / respond / ignore — declared per interrupt.** LangGraph Agent Inbox's `HumanInterrupt` schema exposes `allow_accept`, `allow_edit`, `allow_respond`, `allow_ignore` config flags per interrupt, with `ActionRequest = {action, args}` as the payload and response types `accept | response | edit | ignore`. This is the direct industry answer to "pick a suggestion line verbatim": the proposed action is a structured `{action, args}` object the human can **edit in place** or answer with free text, not a sentence to match. [langchain-ai/agent-inbox](https://github.com/langchain-ai/agent-inbox/)

4. **Escalation calibration is an explicit design goal: "an agent that escalates everything is exhausting to work with, and an agent that escalates nothing is dangerous."** Anthropic's cookbook gate pattern splits the seam into two custom tools — `decide()` for clear-cut cases (auto-handled) and `escalate()` for ambiguous ones (routed to a reviewer); both round-trip through your application, which is where logging and the human queue live. Calibration (not blanket escalation) is the stated objective. This is precisely the "16 of 18 are probe noise" failure mode named and answered. [Anthropic claude-cookbooks — Gate: human-in-the-loop with custom tools](https://github.com/anthropics/claude-cookbooks/blob/main/managed_agents/CMA_gate_human_in_the_loop.ipynb)

5. **Two standard triggers for pulling a human in: failure thresholds and high-risk actions; supervision decays as trust accumulates.** OpenAI's practical guide: set limits on retries/actions (exceeding them escalates), and route *sensitive, irreversible, high-stakes* actions to human oversight — explicitly "until confidence in the agent's reliability grows." Early deployment should lean on human intervention as the eval loop for finding failures and edge cases. [OpenAI — A practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/) ([PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf))

6. **For watchdog/security-flavored agents: pause ambiguous or high-risk actions, and fail closed.** OpenAI's cybersecurity guidance for agentic workflows: give the reviewer *only* the proposed action and the minimal context needed to evaluate it; record decisions and execution outcomes; **fail closed if review times out or becomes unavailable**. Also: put validation next to the tool that creates the side effect, not at workflow boundaries (agent-level guardrails don't run everywhere). [OpenAI — Guardrails and human review (cybersecurity section)](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)

### B. Product patterns (review surfaces in mainstream agent products)

7. **Tiered autonomy ladders, not binary ask-everything/ask-nothing.** Claude Code permission modes form an explicit ladder — `default` (ask for every write), `acceptEdits` (auto-approve in-scope edits + common fs commands), `plan` (read/explore only), `auto` (classifier-reviewed, background safety checks), `dontAsk` (deny anything that would prompt), `bypassPermissions` (isolated envs only) — with allow/ask/deny rules layered on top; deny rules block in every mode. Writes to protected paths are never auto-approved outside bypass. The mode can change mid-session (Shift+Tab cycle). This is the reference model for "which ops actions need approval" tiers. [Claude Code — Permission modes](https://code.claude.com/docs/en/permission-modes) · [Permissions](https://code.claude.com/docs/en/permissions)

8. **Plan-then-approve is the mainstream pattern for "propose actions" — and the plan is editable text with explicit outcome choices.** Claude Code plan mode: agent researches and writes a plan without editing source; on completion the human chooses *Yes + auto mode / Yes + manually approve edits / No, keep planning*, and **Ctrl+G opens the proposed plan in a text editor for direct edits before approving**. Approval exits plan mode and switches to the chosen execution mode. Directly applicable: the ruling face should offer outcome-labeled choices plus an edit-the-proposal affordance, not verbatim selection. [Claude Code — Permission modes (plan mode)](https://code.claude.com/docs/en/permission-modes)

9. **Agent work is reviewed as a PR-shaped artifact: diff + checks + narrated session log + iteration via comments — with safety gating before CI runs.** GitHub Copilot coding agent opens a draft PR, pushes commits as it works, and "logs key steps along the way" (session timeline) so progress is trackable in real time; humans review before merge, and **workflows require explicit "Approve and run workflows" gating** because agent branches can't be trusted to run privileged CI automatically. Iteration = mention `@copilot` in PR comments; GitHub explicitly recommends **batching review comments instead of submitting them individually**; the requester's own approval doesn't count toward required approvals (independent review). [GitHub Docs — Reviewing a PR created by Copilot](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/review-copilot-prs) · [GitHub Blog — Copilot coding agent 101](https://github.blog/ai-and-ml/github-copilot/github-copilot-coding-agent-101-getting-started-with-agentic-workflows-on-github/)

10. **Background/cloud agents review through a queue with verification artifacts, not reports.** Cursor cloud agents: runs appear in a dashboard (cursor.com/agents, iOS app, desktop), each with the conversation, code changes, and **artifacts (screenshots, videos, logs) showing what changed and how the agent verified its work**; humans can send follow-up messages, take over the agent's remote desktop to test the result themselves, and share read-only run URLs with teammates. Entry points live where work happens: Slack `@cursor`, GitHub PR/issue comments, Linear. [Cursor docs — Cloud Agents](https://cursor.com/docs/cloud-agent)

11. **Confirmation UX ground rules (the anti-rubber-stamp canon): specific, consequence-labeled, no default Yes, rare.** NN/g: a confirmation must restate the specific action and consequences in user-centric terms; buttons labeled with outcomes ("Delete file" / "Keep file"), not Yes/No; no default answer; reserve confirmations for serious/irreversible actions (crying wolf destroys their power); prefer offering undo over demanding confirmation; for the most dangerous actions require a nonstandard gesture (type a word) and consider a different human confirming. [NN/g — Confirmation Dialogs Can Prevent User Errors](https://www.nngroup.com/articles/confirmation-dialog/)

### C. Ops & alerting UX (the "18 findings, 16 noise" problem)

12. **The industry noise-reduction ladder: dedup → group → suppress/pause; it learns from human feedback.** PagerDuty's own good/better/best: (good) `dedup_key` so repeat alerts for the same issue collapse; (better) **intelligent alert grouping** — rolling time window + incident <24h old + similarity → related alerts join one incident, instead of dozens of notifications; (best) **pause/suppress alerts that are pure noise and non-actionable**. Crucially, the grouping algorithm *learns from manual merges and manual moves* — human triage actions are the training signal (and PagerDuty warns about overgrouping and recommends starting with a 5-minute window on critical services, widening gradually). This is the exact structural answer to a report bloated with 16 probe-noise rows: dedup by key, group by cause, suppress non-actionable classes, and let rulings feed back. [PagerDuty ops guide — How to reduce noise](https://www.pagerduty.com/ops-guides/ops-practices/reduce-noise/) · [PagerDuty docs — Intelligent Alert Grouping](https://docs.pagerduty.com/ai-automation/aiops/noise-reduction/alert-grouping/intelligent-alert-grouping)

13. **Alert storms are fought with notification grouping + event correlation + scheduled suppression.** Datadog: group similar notifications by service/tag/environment so one issue = one notification; **event correlation treats alerts stemming from the same cause as a single event** (kills duplicate effort across responders); scheduled/ad-hoc downtimes suppress known-window noise (maintenance, planned restarts); composite conditions ("CPU high AND disk high") and anomaly/outlier detection cut flapping at the condition level. [Datadog blog — Combat alert storms](https://www.datadoghq.com/blog/reduce-alert-storms-datadog/) · [Datadog docs — Reduce alert flapping](https://docs.datadoghq.com/monitors/guide/reduce-alert-flapping.md)

14. **Severity-routed delivery + bundling: interrupt only for what needs a human now; digest the rest.** PagerDuty splits high-urgency (push/SMS/phone) from low-urgency (email/mobile, batchable) notification channels, and **bundles multiple triggered incidents into one email** ("You have [3] TRIGGERED Incidents") rather than one message per incident. The generic tiering pattern across ops tooling: critical = immediate multi-channel; medium = scheduled/daily; low = batched digest. [PagerDuty — Email notifications (bundling)](https://support.pagerduty.com/main/docs/email-notifications) · [PagerDuty docs — Notification rules](https://docs.pagerduty.com/account-admin/user-profile/notification-rules)

### D. AIOps propose-then-approve remediation

15. **Governed remediation = action definition + approval gate with three outcomes + execution-time re-check + verification + rollback + audit log.** Port's self-healing pattern: every action has a definition (inputs, scope, expected outcome, success signals, **rollback path**); the approval gate returns **autonomous / needs-approval / blocked** and **re-evaluates at execution time** because incident state changed since recommendation; automation runs under scoped per-action identities (no standing credentials); after execution the runtime verifies against the declared success signals and **auto-rolls back or escalates on failure**; every run lands in the audit log regardless of trigger. [Port docs — Act on response](https://docs.port.io/solutions/self-healing-incidents/act-on-response/)

16. **Humans regulate authority, not each action: a control loop with three states and structured "decision packets."** Port's oversight model moves between *autonomous execution* (confidence above threshold, signals converging), *assisted autonomy* (human tightens constraints while automation keeps running), and *human-led intervention* (verification fails / confidence collapses); transitions are set in policy in advance, "not decided under pressure." When a human is pulled in, they receive a **decision packet**: current state + confidence trend, what was already tried and what happened, remaining options with tradeoffs, and *the specific question the system cannot resolve itself*. [Port docs — Act on response (Human oversight)](https://docs.port.io/solutions/self-healing-incidents/act-on-response/)

17. **Human contact is a structured tool call in the same event log — the "outer loop" pattern.** HumanLayer's 12-Factor Agents, Factor 7: the agent doesn't "talk" to the human; it calls a `contact_human`-style tool whose result arrives asynchronously (Slack/email/webhook) and is injected back into the thread event log. This eliminates the "high-stakes token" choice (prose vs tool call), makes the agent the initiator (agent → human → agent), and — because interactions serialize like any tool call — keeps a **complete audit trail** of every ask and answer. [humanlayer/12-factor-agents — Factor 7](https://github.com/humanlayer/12-factor-agents) (content mirrored at [DeepWiki](https://deepwiki.com/humanlayer/12-factor-agents/3.7-factor-7:-contact-humans-with-tool-calls))

18. **Triage-queue UX conventions: every row says why it's there; decisions are one click and reversible; bulk actions preview their scope.** Review-queue pattern catalog: rows expose reason + enough context for safe triage before opening the full record; actions = claim, assign, skip, **snooze**, escalate, approve, reject, request-changes, mark-reviewed; bulk actions apply only to the previewed selection and report per-row exceptions (stale, already handled, permission-limited); notifications deep-link into the filtered queue. Companion pattern (design blog, secondary): a four-state queue — **active / snoozed (with wake time) / completed / dismissed** — where the primary CTA *is* the resolution, every state change is reversible for a short window (undo toast ~8s), and **dismiss captures a reason because dismissal is feedback to the generator**. [UX Patterns Guide — Review queue](https://uxpatternsguide.com/agent/patterns/review-queue.md) · [Reversible Queue Playbook](https://floramaydc.com/toybox/reversible-queue-playbook/)

## Design implications for IP Radar's five pain points

Mapped 1:1 from the findings; each row = pattern → where it's proven.

| IP Radar pain point | Pattern to adopt | Proven at |
|---|---|---|
| Report blob: 18 "unreachable", 16 probe noise | Noise ladder before surfacing: **dedup key** (source + probe class + error signature), **group by root cause** (e.g. abuse.ch 410 family = one incident), **suppress known-noise classes** until state changes; only items that need a human decision enter the ruling queue — the rest go to the digest. Oversuppression risk is managed the PagerDuty way: start narrow, widen gradually, monitor. | F12, F13 |
| Ruling face requires verbatim suggestion match | Replace with the four affordances: **同意/修改/回复/忽略** on a structured item `{action, args, evidence, blast_radius, rollback}`. Primary CTA executes the recommendation; 修改 edits args in place; ignore = snooze/dismiss **with a reason captured** (that reason *is* the precedent input, same as PagerDuty grouping learning from manual moves). Never require verbatim line matching. | F3, F8, F11, F18 |
| Legal-flavored terms (裁决/判例/台账) | Rename the *surface* to industry-standard verbs (审批/忽略/稍后提醒; 规则/审计日志) while keeping the concept. NN/g rule: labels must state the consequence in the user's terms. "Precedent" survives as a mechanism name (cf. Claude Code allow rules, PagerDuty grouping feedback), not as UI vocabulary. | F11 |
| Manual-only triggers, no notifications | Two-part fix: (1) multiple entry points like @copilot/@cursor — scheduled rounds + on-demand + (optionally) chat mention; (2) **severity-routed delivery**: page-worthy (dead feed affecting coverage, e.g. 410 Gone family) = immediate push; low urgency (probe noise, stats drift) = **bundled digest** ("3 items need review"), deep-linking into the filtered queue. | F9, F10, F14, F17 |
| Markdown blob as the artifact | The package becomes **structured items first, markdown as rendering** (report = view of the item set, never the source of truth). Escalations take the **decision-packet** shape: state + confidence trend, what was tried, options with tradeoffs, the specific unresolved question. Rulings and agent asks serialize into one audit log (Factor 7 event-log pattern). | F16, F17, F9 |
| Approval policy (implicit) | Tiered ladder instead of all-manual: **read-only/analyze = auto**; **reversible, precedented actions = one-click approve or auto after N identical rulings**; **destructive/irreversible = always human, fail closed on timeout**; deny-lists block in every tier (Claude Code model). Approval gate re-checks at execution time; every executed action has a rollback path and post-action verification. | F5, F6, F7, F15 |

## Gaps

- **No direct published critique of "markdown-blob reports vs structured actionable items" as a named topic.** The structured-item conclusion is synthesized from convergent implementations (Agent Inbox schema, Copilot PR artifact, Port decision packets, Factor 7) rather than a single authoritative critique. If a citable argument is needed, the strongest single source is the Agent Inbox `ActionRequest` schema + Factor 7's "high-stakes token" rationale.
- **No quantitative data on approval fatigue / rubber-stamping in agent products specifically** (how quickly humans become yes-clickers when queues are noisy). NN/g confirmation-dialog research is the closest analog and is 2018-era. Could be probed via community threads (Reddit r/ExperiencedDevs on Copilot PR review behavior) if needed.
- **zh-CN terminology conventions not sourced** — the 裁决/判例/台账 rename recommendation follows plain-language principles (NN/g) plus industry verb sets, but no Chinese-market ops-tool UX standard was found; worth a quick Chinese-community check (V2EX/小红书 ops tool screenshots) before finalizing vocabulary.
- **Cursor desktop "background agents" help page returned title-only** — desktop-specific review affordances may differ slightly from cloud agents; low risk since the cloud doc is the current flagship surface.
- **Adoption data for auto-execute tiers** (what fraction of teams actually allow autonomous remediation at which blast radius) not covered — Port/AlertMend describe tiers but publish no adoption stats; if this matters for the ruling, an Opsgenie/Kustomer-style survey search would be the next step.
